# Agent 搜索最小上下文实践

## 问题

编码 Agent 经常需要在大型 Workspace 中定位文件和符号。传统做法按次启动 `rg` 或 `fd`，把扫描顺序中的大量命中直接塞入模型 Context。高频关键词（如 TODO、FIXME）可能一次返回几十条甚至更多结果；若噪声文件排在前面，真正相关的文件会被挤到结果末尾或被输出上限截断。

## 根因

搜索层的第一性目标被误认为“返回尽可能多的文本”。实际上搜索结果是定位线索，不是上下文本身。

## 方案

用尽可能少的上下文把 Agent 带到最可能相关的文件，再按需读取证据。正确工作流：

1. 用模糊查找定位候选文件。
2. 在较小范围内执行 grep 或多关键词 grep。
3. 读取少量关键文件。
4. 只有需要更多证据时才翻页。

工具语义：`find` 用于按文件名、路径片段或概念模糊定位，拿到候选文件后再读取或 grep，不要先遍历整个目录树；`grep` 用于搜索一个符号、字符串或正则，已知大致目录时同时提供相对 `path` 减少噪声；`multi_grep` 一次搜索多个字面量，多个 pattern 是 OR 关系，文件约束只负责过滤文件、不把 pattern 变成正则；首屏未覆盖全部结果时使用返回的 cursor 继续，不能根据首屏宣称“仓库里没有其他命中”。

收益不是“搜索不消耗 token”，而是把 token 用在更可能影响结论的文件上。

## 验证

假设仓库有 33 行 TODO，其中 30 行在一个近期频繁修改但与当前任务无关的噪声文件，另外 3 行在真正相关的实现文件：无排序的全量返回会同时浪费搜索输出 token，并增加关键文件被截断的概率。FFF 按 Git 状态和 frecency 排序、有限首屏 + 分页游标，正确工作流避免该问题。

## 适用范围

大仓库、重复探索、热点文件明显、TODO/FIXME 噪声多、或需要同时定位多个关联符号时价值最明显。小仓库中的一次精确搜索，内置 grep/find 往往已经足够。

## 失效条件

- 首屏没有某个关键词，不代表仓库不存在：FFF 会排序并分页，应增加精确 path/constraints 或沿 cursor 继续。
- FFF 是更好的检索入口，不是穷举证明工具：证明整个仓库绝无某模式需要精确约束、完整翻页，必要时使用确定性审计命令。
- FFF 不替代文件读取、代码理解、测试和验收。
